# Security and resource-use review — 2026-09-24

This review covers the current `codex/security-coverage-20260924` working tree. It is source and local-test evidence, not proof that a cloud image or immutable on-chain contract has changed. V1 v0.21 economic rules and the existing V2 fee/refund rules remain unchanged.

## Confirmed high-severity issue

**S-01 — A rejecting ERC-1155 receiver can block a V2 order book.** In `src/marketplace/OrderbookMarketplaceV2.sol:287-293`, matching sends shares to the bid owner; a receiver revert rolls back the entire match. A rejecting top bid blocks later honest bids until that bid expires. More seriously, `src/marketplace/OrderbookMarketplaceV2.sol:413-426` sends escrowed shares back to an expired ask owner before the order can be removed. If that owner rejects the return, permissionless release and the stale-order cleanup inside `matchOrders` both revert, leaving the ask at the head of that market/outcome book. The adversarial tests `testRejectingBestBidBlocksMatchingUntilPermissionlessExpiryRelease` and `testRejectingExpiredAskCannotBeReleasedAndBlocksBookCleanup` reproduce both cases. Other markets and outcomes have separate books; the test does not establish a global freeze or theft.

The V2 marketplace is immutable, and its factory binds a marketplace once. Do not describe an app, worker, image or source update as a contract fix. A permanent fix needs a separately deployed contract and factory, plus ABI/indexer/SDK compatibility and adversarial accounting tests. A local alert now detects actions stuck at chain preparation for five minutes. The current worker can still recheck such actions every idle poll, so reducing that retry load needs a separate, tested backoff policy; do not pretend a delayed book is healthy. No cleanup fee or refund change is implied by this finding.

## Open operational and dependency risks

**S-04 — The cloud indexer is running the dense default, so sparse RPC savings are not active (operational).** A read-only check on 2026-09-24 found that the running `cpredict-indexer:main-21ec819-20260922` container had no `CPREDICT_INDEXER_CANONICAL_MODE` setting. The code defaults to `dense`; a 35.6-second spot sample observed 152 block-header reads (about 256/minute), including 132 `head` reads. This short sample does not replace a 30-minute acceptance measurement. The indexer was advancing and receipt pending/unresolved were zero, but one observed lag was 25 blocks, above the prior steady-state goal of 20. The local change adds `cpredict_indexer_canonical_mode{mode="dense|sparse"}` so the effective mode can be checked directly. Before claiming RPC savings, explicitly configure and safely validate sparse mode against the existing shadow/rollback criteria, then measure a continuous 30-minute window and provider CU. This review made no cloud changes.

**S-02 — Public RPC spend protection is staged, not yet active by default (medium).** `offchain/app-service/src/rpc-admission.ts` accounts for JSON-RPC subrequests and concurrent upstream calls, but its default `observe` mode permits requests even after a budget is exceeded. Large `eth_getLogs` ranges have a capped estimate rather than a provider CU guarantee. The edge also has request limits, but those do not prove a provider spend ceiling. Review trusted proxy identity and normal traffic, compare estimated units with provider CU, then set `CPREDICT_RPC_ADMISSION_MODE=enforce` in the private deployment configuration. Verify ordinary wallet reads, batches, notifications and one-shot writes before rollout; watch rejected counts and user errors afterward. In-memory budgets are per app process, so a multi-replica deployment needs a shared or edge-wide limit.

**S-03 — Transitive dependency advisory remains (medium, exposure unconfirmed).** The current production dependency audit reports no high or critical findings and six moderate advisories. The actionable chain includes `@zerodev/permissions → merkletreejs → web3-utils → ethjs-unit/number-to-bn → bn.js@4.11.6`, with an infinite-loop advisory on that old `bn.js`. The audit reports no available fix for the direct permission package. Trace whether attacker-controlled input reaches that path before assigning runtime severity; coordinate an upstream-compatible upgrade and rerun SDK signing, permission and browser flows instead of forcing an unrelated dependency override.

## Protections and local work

- V2's `nonReentrant` guard and escrow receipt check were exercised against receiver reentry and unsolicited shares. These tests support those specific invariants; static-analyzer alerts remain candidates until traced.
- Public RPC admission, a configurable keeper per-transaction Gas cap, bounded cleanup quotas, and durable unknown-transaction handling reduce abuse and duplicate-send exposure in the uncommitted service changes. The transaction cap defaults to the daily budget until an operator sets a lower value.
- Claim discovery now uses a transactional financial-fact revision and caches its owner/market directory until the revision or reorg epoch changes. Matching reuses one terminal-state read per market per pinned scan without changing its global candidate order. A proposed 32-order page scan was withdrawn because it delayed later orders and weakened terminal cleanup priority.
- Deployment acceptance still requires current image identity, live RPC/CU and Gas metrics, app/indexer/worker health, reconciliation status, and deployed bytecode checks. Local tests alone do not establish those outcomes.
